Awilix Single Wiring

Every service the orchestrator runs is now built by one awilix container, in scopes per task, per stage and per data source, through registrations the compiler checks. Nothing a task, stage or connector needs is assembled by hand any more, and a missing or mistyped registration fails tsc or a test that resolves every token. Behaviour is unchanged apart from two named fixes; the suite went from 1974 to 2015 tests.

Summary

  • One entry point. createRootContainer(config, { rootDir }) builds the root container; src/index.tsx and the two scripts that run tasks take .cradle from it, and the orchestrator and dashboard server resolve from it.
  • Scopes for the per-task and per-stage objects. A task scope holds the task's compose client, log collector, workspace cleaner and container manager; a stage scope holds one stage's executor; a data-source scope holds a connector and its poller.
  • A cradle the compiler checks. src/di/registration.ts adds wiring<C>().service, factory, Registrations<C> and asValues. Each registration site is a typed object; a missing token, an extra token or a constructor whose deps the cradle cannot provide fails tsc.
  • New: src/di/registration.ts, src/container/container-manager-factory.ts, src/container/stage-executor-factory.ts, src/container/cli-executor.ts (the executor interface alone).
  • Deleted: CliExecutorFactory, buildContainerFactory, buildComposeClient, createCradle, and the stateless classes ComposeFileResolver, LogSourceRegistry, AgentCatalogProvider, JitMcpConfigWriter, SkillTemplateRenderer, both agent-writer classes and both VCS provider client classes, with their interfaces and mock factories.
  • Became functions or plain objects: resolveComposeFiles, registerLogSources, loadAgentCatalog, writeJitMcpConfig, renderStageSkills, claudeAgentWriter, copilotAgentWriter, adoVcsSourceProviderClient, githubVcsSourceProviderClient.
  • Two deliberate behaviour changes: JIRA polling and retry warnings reach the activity log, and scripts/lookup-users.ts authenticates with its data source's JIRA credentials.
  • Docs: docs/dev-doc/dependency-injection.md rewritten; AGENTS.md § Adding a DI service, ARCHITECTURE.md, the stack profile, the testing rule and two dev skills follow the code.

In plain terms

The orchestrator is made of a few dozen collaborating parts: one that talks to JIRA, one that tracks which comments it has acted on, one that starts the Docker stack for a task, one per AI command line that runs an agent, and so on. Something has to create each part and hand it the other parts it needs. Before this change, most parts were created by a dependency container, but the parts that live for a single task or a single stage were assembled by hand in a handful of factory functions, and the container's own list was only loosely checked.

Now the container creates everything, and it does so in nested scopes. The outer scope lives as long as the process. Each task opens a scope of its own for the parts that belong to that one task, such as its Docker stack, and each stage of the task opens a smaller scope inside it for the agent runner of that stage. When the task ends, its scope is dropped and nothing of it lingers. JIRA sources work the same way: each configured source gets a scope that holds its client, connector and poller.

The list of what the container can create is a typed description, and the compiler compares every entry against what each part asks for. Forgetting to register something, misspelling it or handing a part the wrong kind of thing stops the build instead of failing at three in the morning on the first task that needs it. A test then asks the real container for every single part, in every scope, to catch the few mistakes a compiler cannot see.

Parts that never held any state of their own, and only ever read files from a fixed place, stopped being classes and became plain functions, so there is less to create and nothing to wire for them.

Walkthrough

1. Checked registration helpers

src/di/registration.ts:26 defines Registrations<C>, which maps every token of a cradle type to a resolver of that token's type: an object typed with it fails tsc on a missing or extra key. wiring<C>() at :35 returns service, which accepts a class only when cradle C provides every key of its deps object with a compatible type, optional keys included, and factory. asValues at :52 turns a typed values object into value registrations. tests/di/registration.test.ts holds the @ts-expect-error cases.

const w = wiring<OrchestratorCradle>();
const root: Registrations<Omit<OrchestratorCradle, "connectors" | "pollers">> = {
  ...
  taskRunner: w.service(TaskRunner).singleton(),   // delete this line → TS2741 names taskRunner
};

2. The root container

createRootContainer (src/awilix-cradle.ts:138) registers the root object, then registerScopedServices (:114), which puts the task and stage registrations at the root as .scoped(), then builds the data-source maps and registers connectors and pollers as values with a satisfies Registrations<Pick<…>> check (:207). The root object includes containerFactory, orchestrator and dashboardServer, so src/index.tsx only destructures them.

3. Data-source scopes, built outside resolution

buildDataSourceMaps(container, config) (src/datasource/registry.ts:65) opens one scope per dataSources entry and hands it to the type's registered factory. The JIRA factory (src/datasource/connectors/jira/factory.ts:69) registers its connection, client, connector and poller in that scope. The maps are built after the root registers, never inside a root singleton's resolver: awilix shares one resolution stack with child scopes, so a scoped resolve under a singleton fails its lifetime check (spec Correction 2, reproduced on awilix 13.0.5). resolveJiraConnection (:57) is the one place that parses a JIRA connection and reads its JIRA_PAT_<KEY> and JIRA_EMAIL_<KEY>; the factory and both JIRA scripts use it.

4. Task scopes

openTaskScope(container, values) (src/container/container-manager-factory.ts:17) opens a scope with the task's profile and workspacePath, resolves its compose client once and registers it back as a value, then registers stageExecutors. A scoped registration caches in the scope that resolves it, so without that pin each stage scope would build its own compose client and re-run the squid.conf check. createContainerManagerFactory (:38) keeps the ContainerManagerFactory interface: create resolves the task's containerManager, forceDown resolves only compose, and createLocalSession opens a host stage scope from the root for a post-task hook.

const scope = container.createScope<TaskCradle>().register(asValues(values));
scope.register({ compose: asValue(scope.resolve("compose")) } satisfies …);   // one client per task
return scope.register({ stageExecutors: asValue(createStageExecutorFactory(scope)) } satisfies …);

5. Stage scopes, one cradle per executor kind

createStageExecutorFactory(taskScope) (src/container/stage-executor-factory.ts:82) switches on the stage's CLI. A Claude Code stage loads the agent catalog and opens a ClaudeStageCradle scope with the stage root's name and subagent depth; a Copilot stage opens a CopilotStageCradle scope and loads no catalog. createHostStageExecutor (:118) does the same for host stages, computing the pinned binary, the hooks directory and the reachable subagent names. Host cradles build on the root cradle, so a variant's own mode: "local" stage opens one from the task scope and a post-task hook opens one from the root.

The executors take stageProfile and containerLogger, cradle tokens beside the task's profile and the orchestrator's logger. Swapping one for the other still type-checks, so four tests in tests/container/stage-executor-factory.test.ts ("runs a … stage with the stage's agent, model and timeout and logs to the container logger") run a stage whose task profile and stage profile differ, and assert the argv carries the stage's agent, model and timeout and that the log line reached the container logger.

6. Stateless classes as functions

Classes whose only input was the checkout root became module functions taking rootDir: resolveComposeFiles (src/container/setup/compose-files.ts:19), registerLogSources (src/container/log-source-registry.ts:35), loadAgentCatalog (src/container/setup/agent-catalogs.ts:12), writeJitMcpConfig (src/container/setup/jit-mcp-params.ts:102) and renderStageSkills (src/container/setup/skill-includes.ts:128). The agent writers and VCS provider clients became plain objects that satisfy their interfaces. HookRulesRedactor stays a service: it reads only rootDir but spawns perl behind ITextRedactor.

7. Everything rooted at rootDir

The repo cache, compose files, squid.conf, the shared hooks path, the activity log and the task workspace all resolve against the cradle's rootDir. buildTaskContext (src/services/task-context.ts:53) takes it from the orchestrator, so a container built with a root other than the current directory clones and mounts in one place. Production passes process.cwd(), as before.

8. The two behaviour changes

  • JIRA logging. The JIRA client and poller take the activity-log logger, so polling progress and retry warnings reach output/logs/activity-*.log. Before, no caller passed them a logger and retries were silent.
  • lookup-users credentials. The script reads the selected data source's connection and credentials through resolveJiraConnection, so it authenticates the way the orchestrator does.

9. Proof it is complete

  • The test "resolves every root registration from the root container to its class or value" and its task-scope sibling in tests/orchestrator-factory.test.ts resolve every registered token under strict mode against a fixture checkout, and compare against tables keyed by the cradle types, so a new token fails lint until it has an expected class. Deleting one stage registration line passes tsc and fails this test.
  • The spec's three completeness greps return only named exceptions: scripts/lookup-users.ts builds one JiraClient with the console logger scripts use, and two superseded planning notes under plans/ and todos/ keep their old class names.
  • Deleting taskRunner from the root object fails tsc with TS2741 naming the token.

Left alone on purpose

  • A missing profile squid.conf still throws from containerFactory.create outside TaskRunner's try, as it did before; filed in todo.md.
  • ContainerManager's test-only containerLogger? fallback, the dashboard WebSocket server binding every interface, the JIRA poller's console.error and the dead JiraFieldExtractor and JiraIssueParser: all pre-existing, all filed.
  • Derived interfaces (type IFoo = PublicApi<Foo>) were deferred by the owner before the work began.

Check yourself

Why does openTaskScope resolve compose and register it back as a value?

Because a .scoped() registration caches in whichever scope resolves it. Each stage scope is a child of the task scope, so without the pin every stage would build a second ComposeClient and re-check squid.conf. As a value, the one client is what every child resolves. src/container/container-manager-factory.ts:24; the test "hands its stage scopes the task's compose client".

Why are the data-source maps built after the root registers, instead of inside a root singleton's factory?

awilix 13 shares one resolution stack between a container and its child scopes. Resolving a scoped JIRA registration while a root singleton is being resolved fails the strict lifetime check. Building the maps in plain code after registration avoids that. Spec Correction 2; src/awilix-cradle.ts, after registerScopedServices.

A test-only constructor option, like ActivityLog's ring-buffer size, is a second positional parameter. Why not an optional key on the deps object?

Under InjectionMode.PROXY with strict: true, destructuring a key the cradle doesn't hold throws, even when the key is optional. awilix passes only the cradle, so a positional parameter stays undefined in production and tests can set it. Spec Correction 1.

What would happen if a Claude Code executor read profile instead of stageProfile, and what catches it?

It would run the variant's first agent, model and timeout instead of the stage's. Both tokens are IAgentProfile, so it type-checks. The four rename-guard tests in tests/container/stage-executor-factory.test.ts give the task and the stage different profiles and assert the stage's agent, model and timeout in the argv.

Why are there four stage cradle types instead of one?

The per-stage values differ: a Claude Code stage needs its root agent's name and subagent depth from the catalog, a Copilot stage loads no catalog, and host stages need a binary and a workspace and have no task scope when they run as post-task hooks. One cradle would force Copilot stages to load the catalog or leave values unregistered. Spec §2 and Correction 5; src/awilix-cradle-types.ts.

Where can a post-task hook's host stage scope open from, and why?

From the root. Hooks run after teardown, when the task scope is gone, and host stage cradles read no task token, so the root holds all they need. A variant's own local stage opens the same kind of scope from its task scope. createLocalSession and createHostStageExecutor; spec Correction 11.

Which mistakes does tsc catch, and which does only the all-token test catch?

tsc catches a missing or extra token, a resolver of the wrong type, and a constructor deps key the cradle lacks or types differently. It cannot see a wrong lifetime, a registration line deleted from a scoped group, or a deps key swapped for another token of the same type; the all-token test and the rename guards catch those. docs/dev-doc/dependency-injection.md, "What tsc checks".

Why did continuationRunner and sessionRunner become root singletons without changing behaviour?

Their fields are read-only dependencies and all their state lives in run()'s locals, so one instance serves every task. Before, a fresh pair with identical dependencies was built per task. Spec §4; confirmed by the interim and final reviews.
